# Windows先読みと補正の選択

対象はWindowsのRustアシスト経路。通常のSwift変換・Swift側のタイポ補正とは別である。

## 生成と表示

- 通常変換の応答後、60ms入力が止まると補正 (`kind=1`) と先読み (`kind=2`) を別RPCで要求する。生成枠も別で、先読みは補正モデルの終了を待たない。
- 補正は手動提案なら先読みの応答まで保留する。先読みが先に届けば直ちに表示できる。自動反映できる狭い根拠の補正は保留しない。
- 入力・候補・COM context/composition・文脈・設定・要求世代が一致する結果だけ反映する。片方を追加した際だけ、その追加後の候補を次の結果の照合対象にする。
- 自動/Tab補正は未確定のまま反映し、直後のEscで元の打鍵履歴へ戻す。補正後は文脈のepochを同期して先読みだけを再要求する。
- 表示中のTab対象は次の編集まで固定する。遅い手動補正が届いても表示済み先読みを置き換えない。補正は通常候補一覧の「補正」からも選べる。
- 先読みは追加部分と「Tabで確定」を表示する。補正の提案は「Tabで補正」、適用済み補正は「Escで戻す」。先読みと補正の取消表示は共存できる。
- 先読みのTabは現在の表記＋追加部分の全文を確定する。弱い補正を未採用のまま先読みへ混ぜない。

## 妥当性の初期評価

RPCの `relevance` は根拠に基づく順序値であり、モデル確率や正解率ではない。

| 候補 | 値 |
|---|---:|
| 一意な近接キー復元等、自動反映の根拠がある補正 | 100 |
| 学習済みの手動補正 | 70 |
| 表記を維持し、出力検査を通過したモデル先読み | 60 |
| 独立した根拠のないモデル・規則補正 | 30 |

最初の表示時点で揃っている候補の値を比較する。同値では先読みを選ぶ。出力検査は文脈への完全な意味適合を保証しない。確率の校正や学習した妥当性判定器は未導入。

## 先読みの入力とモデル

読み・通常変換済み表記・追加部分を別々に扱う。先読み候補はZeroCon Modelだけで生成する。定型句・共起表・採用履歴による候補生成とLFM先読みは使用しない。モデルが不通、または出力検査に不合格なら先読みを表示しない。

発火は読みの末尾がひらがな・カタカナ・長音「ー」・日本語句読点のいずれかのときだけとし、末尾が数字・記号・英字なら推論・キャッシュ・HTTP要求を行わない。

ZeroConは、`EE02 + 左文脈 + EE00 + カタカナ読み` から読みの続きを生成し、短い句の境界までを取り出す。その後 `EE02 + 左文脈 + EE00 + 延長した読み + EE01` で表記へ変換する。変換結果が現在の表記で始まらなければ破棄する。生成かなをそのまま本文に追加しない。

- 読み生成24トークン・250ms、表記変換は入力長に応じ最大256トークン・300ms。左文脈は末尾256文字。
- 生成上限で切れた断片、制御文字、記号だけ、表記の繰り返し、原表記の変更を除外する。読みの生成上限に達しても、その前に完結した短い句があれば利用する。
- 学習文の「この記事」「上記」等を文脈の根拠なしに追加する出力を除く。ただし根拠のない地名や内容まで網羅して判定する機構ではない。
- 補正後のdirect入力表記に漢字がある場合は、背景ワーカーで逆引き辞書から読みを復元する。復元できなければ先読みは省く。
- モデルキャッシュはポート/左文脈/読み/表記をキーに32件。設定再読込時に消去する。

## 起動と設定

| 用途 | 接続先・モデル |
|---|---|
| Rust補正・ZeroCon先読み（統合） | 18091、実行フォルダの `zenz.gguf`（メイン変換モデル）、漢字変換と共通の `zenzai.backend`（既定Vulkan、CPU/CUDAも選択可） |
| 設定画面のベンチマーク | 8090。実IMEの先読み・補正とは別プロセス |
| （旧構成）Corrector専用 | 18090。v0.2.3で完全撤廃され、18091のメイン変換モデルへ一本化 |

launcherはAIアシスト有効時に常駐推論サーバー（ポート18091）を監視する。従来の独立したCorrectorサーバー（18090番）は廃止され、メイン変換モデル1本で先読み・タイポ補正（2段リランキング）・漢字変換を担う。先読みモデル選択は廃止し、旧 `experimental_predictive_model` は読み込み時に無視・次回保存時に除去する。タイポ補正の `experimental_ai_engine` は先読みには影響しない。所有するプロセスだけ設定変更・異常終了に応じて停止/再起動する。Job Objectによりlauncher終了時も先読みプロセスを終了する。外部の待受プロセスは停止しない。

モデル切替時はセッション内の一時イベントで先読み停止を要求し、launcherが所有プロセスの停止を確認してから重みを差し替える。変換側のwatchdogも切替中の再起動を待つ。設定アプリの終了・エラー時にはハンドル解放で待機を解除する。コピー失敗は設定画面へ返す。

先読みの採用履歴と採用通知は廃止した。旧クライアントの通知は互換性のため認証後に無処理で応答し、compositionの所有権を取得しない。タイポ補正の学習データは維持する。

設定画面のAIアシストベンチマークも同じZeroCon生成・出力検査を使用する。専用8090番で漢字変換と同じバックエンドを起動し、定型句でモデル評価を代用しない。補正のベンチマークは既存の規則による簡易評価で、実IMEの統合補正評価とは区別する。

## 検証

`windows/` から:

```powershell
cargo test -p azookey-server --lib --offline
cargo test -p azookey-server --bin azookey-server --offline
cargo test -p azookey-windows --lib --offline
cargo test -p launcher --offline
node --test crates/ui/tests/ruby_reading.browser.mjs
```

サーバーのbinテストはSwift/llamaのDLLがPATHに必要。ユーザーの補正履歴に左右されないよう、テスト用AppDataを指定する。ブラウザテストは `PLAYWRIGHT_MODULE` / `PLAYWRIGHT_CHANNEL` を既存環境に合わせる。

実モデルの生成評価は検証専用endpointを起動し、`ZEROCON_PREDICTION_TEST_PORT` を指定して `cargo test -p azookey-server --lib --offline live_prediction_evaluation -- --ignored --nocapture` で行う。これはモデル経路の評価であり、実IME操作の代用ではない。

同じソースからビルド・導入したIMEで、`yorosikuonegaisi` → 待機 → Tab、`okseri` → 補正 → 待機 → Tab、同じ補正後のEscを確認する。さらに打鍵途中・結果到着前後のBackspace/Delete、左右移動、Space候補選択、Enter確定、Esc取消、フォーカス/アプリ切替を順に記録する。古いDLLを保持する入力先アプリは開き直す。

次の品質評価では、正常入力への誤補正・補正取消率・先読みの採用/出現率・打鍵削減・候補の変更回数・停止から表示までの遅延を一緒に比較する。出現率を落としただけの精度改善を採用しない。
