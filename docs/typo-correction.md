# Windowsのタイポ補正

`general.experimental_ai_assist` がRust側の補正・先読みを有効にする。通常のかな漢字変換とSwift側の `experimental_typo_correction` は別経路である。

## 表示と操作

| 状態 | 本文 | 原文フローティング |
| --- | --- | --- |
| 補正不要・通常の先頭候補と一致 | 通常のライブ変換 | 原文のみ |
| 補正の提案 | 通常のライブ変換 | 変更前 → 変更後、Tabで補正 |
| 根拠の強い補正・Tabで採用済み | 補正後の未確定文字列 | 補正済み、Escで戻す |

- Tabで補正しても確定せず、続けて入力できる。先読みのTabは従来どおり採用・確定する。補正の存在だけで先読みを止めず、根拠値からTab対象を選択する。補正後も先読みを再要求する。詳細は [predictive-assist.md](predictive-assist.md)。
- 補正適用直後のEscは原文の打鍵履歴と表示を復元する。同じ入力状態では取り消した候補を再表示しない。通常の編集・候補操作後は通常のEsc動作に戻る。
- Enterは本文の表示を確定し、未採用の提案を自動採用しない。Spaceで開く候補一覧には補正候補を2番目に「補正」表示で含め、通常候補の相対順とIDは維持する。候補選択開始後に背景の結果で並びを変更しない。
- Backspace/Deleteは通常の編集。元のローマ字からの削除はSwiftの正規打鍵列を使い、1文字の削除をraw入力の1文字削除と仮定しない。
- 変更箇所を強調し、長文の共通部分は省略する。操作表示を残して折り返す。明暗テーマ・拡大率に対応し、ネイティブ側の画面端配置を維持する。

## 補正経路

1. 通常変換のAppendText/ReplaceCompositionはモデル補正を待たず応答する。日付・計算などの決定的なマクロは即時に追加する。
2. クライアントは入力・候補・COM context/composition・接続/文脈・モデル設定・要求世代のスナップショットを作る。60ms入力が止まると `GetAssistCandidates` を別タスクで呼ぶ。
3. サーバーはSwiftやcompositionの変更ロックを使わず、専用ワーカーで補正と先読みを生成する。補正と先読みは独立したRPC・生成枠を使い、各枠の推論は1件。HTTP読取量・時間、候補数、キャッシュ件数を制限する。
4. 25msのTSFスレッドタイマーで結果を受け取る。削除・再入力・候補操作・文節移動・確定・フォーカス変更等で世代や状態が変わった結果を破棄する。同じ文字列を打ち直した場合も古い結果を使わない。
5. 補正は元の候補を保持して追加する。適用時に補正表記をdirect入力としてconverterへ絶対置換し、原文のcompositionと入力ledgerを復元用に保存する。補正適用とアプリへの確定は別操作。補正直後は自動確定の安定性履歴を作り直す。

v0.2.3以降、従来の独立したCorrectorサーバー（ポート18090）および専用モデルは完全撤廃され、ネイティブワーカー（`keyboard-prior.exe`）による探索とメイン変換モデル（ポート18091）による2段リランキング（Stage-1/Stage-2）・漢字変換へ統合された。

1. **Stage-1（高速Viterbi辞書探索と読み尤度判定）**:
   - `keyboard-prior.exe` の `--assist` モードにより、1キー編集（削除・挿入・QWERTY隣接キー置換・母音置換・隣接転置・母音隣接 `a` 混入・`っ/ん/ー` 増減・半濁音/タ行サ行混同など）を考慮したヘボン式・訓令式双対の候補（最大24件）を高速生成。
   - `reverse-v2.bin` に基づく単文字特殊モーラ上限（`-20.0`）や助詞外断片上限（`-11.0`）、文節境界ペナルティにより、細切れの断片より正規の単語を確実に上位化。文字挿入による正規単語復元時はトークン長補正（`len_comp`）を付与。
2. **Stage-2（変換表層形を含めたリランキング）**:
   - Stage-1 で閾値（$\Delta \ge 37.0$）を超えた上位最大3件の読み候補について、辞書最適変換表層を連結した系列 `\u{EE02}{context}\u{EE00}{reading}\u{EE01}{surface}` をメイン変換モデル（18091番）でバッチ評価し、表層対数尤度を加算してリランキング。タイポ発火判定自体をStage-1でゲートするため、正常入力の誤補正0%を厳密に維持。
3. **逆引き辞書検証と第2候補フォールバック**:
   - `reverse-v2.bin` のマルチパス Viterbi 探索（`reading_check.rs`）で変換結果の読み整合性を検証。第1候補の変換結果が読み検証を通過しなかった場合、第2読み候補（`alt_reading`）へ自動フォールバック。

自動反映は、完全な辞書語へ一意に復元できる隣接キー誤入力、または同じ補正を明示採用して確定した記録が3回以上ある場合に限定する。モデル確率を正解率として扱わない。末尾が入力途中の子音、全体が英字だけの識別子、曖昧な候補は自動反映しない。自動反映だけで採用回数を増やさず、取消・未確定・確定失敗を学習に数えない。

通常変換・タイポ補正・先読みはすべてポート18091のメイン変換モデル（Nano v4等）1本で処理される。旧18090番Correctorサーバーは存在しない。設定・辞書・重みのファイルと実行パスを確認して評価する。

## 検証

`windows/` で実行する。

```powershell
cargo test -p azookey-windows --lib --offline
cargo test -p azookey-server --lib --offline
# Swift DLLと依存DLLがPATHにある環境
cargo test -p azookey-server --bin azookey-server --offline
node --test crates/ui/tests/ruby_reading.browser.mjs
```

ブラウザテストはPlaywrightが必要。`PLAYWRIGHT_MODULE` にモジュールのURL、必要に応じ `PLAYWRIGHT_CHANNEL=chrome` を指定する。実際のHTMLを描画し、旧形式・構造化形式の表示、Tab/Esc、画面幅、拡大率、明暗テーマを検証する。

`test_live_server_okseri` と `test_ui_show_pill` は実行中IMEへ接続するため通常テストではignoreする。前者を明示実行すると、順番に `o k s e r i` を入力し、非同期候補、direct適用、`m a`の追加入力、1文字削除、カーソル移動、元の打鍵履歴への復元、再度の削除を実サーバーで検証する。空き状態かつ同じソースからビルドしたIMEに対してのみ実行する。

```powershell
cargo test -p azookey-windows --lib --offline test_live_server_okseri -- --ignored --nocapture
```

このRPC検証とモデル評価だけでTSFの実操作成功とは判定しない。新しいDLLをロードした入力先アプリで、表示、入力継続、Tab、Esc、Space、Enter、取消、フォーカス移動も確認する。既存アプリは更新前のDLLを保持するため、IMEプロセスの再起動後に入力先アプリも開き直す必要がある。
