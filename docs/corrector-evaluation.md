# 補正モデルの評価契約

現行300問は固定の合成回帰セットとして保持する。Windows IMEの実用精度、入力頻度に重み付けした誤補正率、
自動適用の安全性をこの1本の点数で代表させない。2026-10-30の具体的な監査は
[監査・追加学習記録](../reports/typo-assist/corrector-v4-advanced-and-benchmark-audit-20261030.md)を参照。

## 三つの層を分ける

| 層 | 入力と出力 | 主に調べること |
|---|---|---|
| モデル単体 | 実際のprompt → 生の生成 | 正しい読みの復元、正しい表記、EOS到達、余計な生成、正常入力の保持 |
| 補正ポリシー | 入力・文脈・独立に生成した通常候補 → 提案・自動適用判定 | 提案の適合率、取りこぼし、正常入力への誤提案、辞書・保護規則による拒否 |
| 実IME | 順序付き打鍵・削除・移動・採用・取消 → 未確定状態・確定文字列 | 操作数、復元の正確さ、古い結果の破棄、打鍵から表示までの遅延 |

通常候補へ正解を注入しない。oracle診断だけは正解表記をモデル応答として渡し、
「正しく生成できた場合に現在のポリシーが通すか」を測る。oracleの成績・遅延をモデルの実測値に混ぜない。

## 指標

- **タイポ修復の再現率**: 正しい補正候補を返したタイポ / 全タイポ。無提案も取りこぼしに数える。
- **提案の適合率**: 正しい補正候補 / 全補正候補。正常入力へ誤提案したものも偽陽性に含める。
- **正常入力への誤提案率**: 不要・誤った補正候補が出た正常入力 / 全正常入力。
- **通常候補との合算正解**: 通常候補または補正候補に許容正解があるタイポ。補正モデル単独の正答数と区別する。
- **自動適用**: 正しい自動適用 / 自動適用した件数、誤自動適用 / 全正常入力、適用のカバー率を併記する。
  「誤り0件」には必ず適用した件数を添える。
- **遅延**: モデル・補正処理・実IME表示を分けてp50/p95/p99を反復測定する。通信失敗・打切り・無提案も別に数える。

採用指標にF0.5を用いる場合は、単位を明記する。現行監査スクリプトのF0.5はケース単位であり、
GECの編集span採点そのものではない。precisionを重視する設計の参考は
[BEA 2019 Shared Taskの評価規定](https://www.cl.cam.ac.uk/research/nl/bea2019st/)。
層の異なる総合点を足したり、純粋なかな漢字変換率と補正の再現率を同じ難易度の率として比較しない。

## 次のWindows用ベンチマークに必要な情報

1. 元文・元読みのグループを先にtrain/validation/locked testへ分け、その後に誤りを作る。
2. `canonical_keys`、`observed_keys`、編集位置・前後キー・誤りの種類、変換器の実装・revisionを保存する。
   Pythonの近似ローマ字変換を実IMEの状態として扱わず、実際の変換器に打鍵を通した未確定読みも保存する。
3. 正解の読みはかなで検証し、漢字交じりの「読み」、誤読、無関係な追記を分離する。
4. `expected_readings`、`expected_surfaces`、`expected_action`（提案・保持・待機）を分ける。
   表記の別解は事前レビューで固定し、モデル出力を見て採点を有利に変更しない。同音なら何でも正解にはしない。
5. Windows QWERTY、かな直接入力、モバイルフリックは別集計とする。
6. 正常語、固有名詞、英数字、URL、コード、句読点、混在入力、未確定子音、連続打鍵中、複数誤り、曖昧な文脈を含める。
   修正すべきでない入力と、入力途中なので待つべき状態を十分に用意する。
7. 同じ語句の変異を何件も作った場合、ケース単位のmicro値と元文グループ単位のmacro値を併記する。
   信頼区間も元グループの依存を考慮する。正常45件の単純な二項区間を実使用の安全性保証にしない。
8. モデル・データ・辞書・通常モデル・実行器・ポリシー・設定・各出力をハッシュ付きで保存する。

QWERTY用には、元グループを分けた後に新しいキー誤りを作り、Windowsの実際のComposingText DLLへ
順番に渡す合成データと、修復/保持/待機を分けた固定ポリシー評価を追加した。
手法・データのハッシュ・退行を含む結果は[QWERTY専用corrector記録](../reports/typo-assist/corrector-qwerty-v4-20261030.md)を参照。
この追加学習にはフリック誤りを混ぜず、フリック用モデルは別に評価する。
保存したrawキーはデータの由来であり、従来のcorrector promptへ新しく渡す推論入力ではない。

評価用の`--replay`は、ケースIDと完全一致するpromptごとに実際のモデル応答を再生する。
正解表記を応答へ注入する`--oracle`とは別モードであり、live評価と提案・自動適用判定の一致を確認する。
replay内の処理時間をモデル推論や実IMEの遅延として使わない。
元グループmacro値とグループ単位のpaired bootstrapもmicro値に添える。

現状も過去の開発元グループを再利用した合成評価であり、独立した実打鍵のlocked testや、
大量の実IME操作評価が整備済みであるとは扱わない。正常かなに加え、削除後prefixを保持対象として
分けて数える。表記別解を十分覆えない完全一致採点と、同音異義語を区別できない読み一致診断を混同しない。

## ツール

```powershell
cargo build --offline --manifest-path engine/rust/Cargo.toml --target-dir artifacts/build/corrector-audit --example evaluate_corrector
python scripts/run.py benchmarks/research/benchmark_corrector_pipeline.py --oracle --corrector <実在する参考GGUF> --normal <通常モデルGGUF> --runner artifacts/build/corrector-audit/debug/examples/evaluate_corrector.exe --out artifacts/results/<新規oracle名>.json
python scripts/run.py benchmarks/research/audit_corrector_benchmark.py --oracle artifacts/results/<新規oracle名>.json --model model=artifacts/results/<通常の補正評価>.json --out artifacts/results/<新規監査名>.json
```

localhost通信を許可した環境で専用サーバーを起動する。既存の結果や評価問題は上書きしない。

## QWERTYキー・編集状態の研究比較

`data/build_qwerty_state.py`は既存のnative観測へ、観測可能な`input_state`（append/backspace/unknown）と
rawキー単位のカーソル位置を追加する。backspace例はDLLへ元キーを入れて実際に削除し、観測読みの一致を検証する。
現状は末尾編集を合成したデータであり、実ユーザーの操作記録ではない。
raw不明の既存正常行へキーを捏造しない。

`training/qwerty_input_contract.py`の`raw-state`契約は、PUA入力区切りの直後にASCII JSONのキー列・編集種別・
カーソル位置を追加する。正解、正規キー、誤り位置、誤り種別、期待動作はpromptに入れない。
モデルへの入力契約が変わるため、従来GGUFとの単純な置換はできない。`kana`契約を対照として同条件で学習する。
校正用imatrixも選んだ契約でtrain行だけから生成する。

`benchmarks/research/compare_qwerty_state.py`はQ4量子化を事前に固定し、従来モデル・対照学習・raw-state学習を比較する。
「無処理／削除状態の保護／1回のキー編集で説明できる提案だけを通す保護」を全モデルへ同条件で適用する。
後者は近似ローマ字decoderで探索を絞り、採用する編集列をnative DLLで再検証する。近似探索が見逃す可能性は残る。
raw不明の例はキー検査を省略する。未知のキー列を正常入力扱いして全提案を落とすことはしない。
これはオフラインの候補抑制実験であり、学習済みrerankerやリアルタイム実IMEの実装ではない。
個別の生成promptと応答、辞書・ソース・fixture・モデルの識別情報を保存し、再生時間は遅延として扱わない。

`data/build_qwerty_fresh_eval.py`は学習中に新たに作成し、比較前に固定した20文章の合成評価を作る。
既存train/val/testとのテキストキー重複を検査するが、事前学習由来の非重複や人による意味審査は保証しない。
この追加セットも実打鍵の封印評価を代替しない。

## 読み候補探索の追加経路

`qwerty_reading_search.py`は観測キーから元入力を含む最大24読みを作り、候補キー列をnativeで検証してNano v4で採点する。
`evaluate_qwerty_reading_surface.py`は既存提案を保持し、無提案だったケースだけ候補読みを固定通常モデルで表記へ変換する。
追加候補は表記・読み整合を検証し、手動採用に限定する。元のRust補正ポリシーへ再投入した比較ではなく、
物理キーの証拠を使う別の研究経路を含むため、通常候補・生生成・最終追加候補を区別して保存する。
読み段と表記段は各々validationだけで校正する。読みの正解数を表記の正解数に加えない。
既存の誤提案を維持する追加方式なので、修復数と誤提案数を必ず併記する。
結果と追加処理だけのCPU遅延は[読み探索の記録](../reports/typo-assist/corrector-qwerty-reading-search-20261030.md)を参照。

## 単一correctorの局所修復契約（研究用）

`training/qwerty_local_contract.py`の局所方式は、raw-state入力から次のいずれかを生成する。

| 出力 | 意味 |
|---|---|
| `K` | 入力を保持する |
| `W` | 入力途中として待機する |
| `E:before:after` | 観測キー内の一意なbeforeをafterへ1回だけ置換する |

beforeは最大12文字、afterは最大14文字。重なった出現も含めて一意かを確認する。
変更後の全キー列が1回の物理編集で説明でき、nativeで完成かなへ変換できた場合だけ修復として受け付ける。
正規キーを読むのは教師ラベル作成時だけであり、実行時の適用関数は正解・誤り位置を受け取らない。
K/Wは補正表記を生成しない。Eの読みは既存の通常モデルで表記へ変換し、読み整合を検証する。
この方式に、推論時の候補列挙や別の読み採点モデルは必須ではない。

`train_qwerty_local.py`は同じNano v4、観測入力、学習行、重み付け、DoRA条件で、全文表記と局所指示を比較する。
両方式に同じ長めの合成入力を加える。テンプレート語句は同じsource group内で増補し、評価の文章を再利用しない。
出力長が異なるので、checkpoint選択の比較指標は正解表記への完全一致ではなく、意図した読みへの修復と保持/待機の誤提案で揃える。
全文方式は辞書読み整合、局所方式は実際のpatch適用後のnative読みで判定し、表記の意味的な正しさとは区別する。

最終GGUF評価は、モデル単体の無保護指標と、共通の入力途中/削除保護を適用した表記指標を両方保存する。
局所方式はnormalモデルの変換を含むため、推論段数の違いも明示して時間を比較する。
不正な局所指示は無提案だが、修復対象の分母から除外せず取りこぼしとして数える。
raw不明の例では局所指示を適用できないため、その正常保持を一般の誤補正耐性の証拠と混同しない。
製品のRPC・IMEにこの契約が適用済みとは扱わない。
全文方式の提案にもnativeで検証した1キー編集の証拠を求めるphysical層を別に採点し、
局所指示が必須にしている物理編集制約と比較する。raw不明で検証できない場合はこの層では提案しない。
同条件学習と不採用候補を含む結果は[全文生成と局所修復の記録](../reports/typo-assist/corrector-qwerty-full-vs-local-20261030.md)を参照。

### 修復損失の比較

`train_qwerty_local.py --repair-weight`は、正しい局所指示と`E:before:before`という誤ったコピー指示をBPE単位で比較し、
差分に当たる教師tokenのCEを重くする。例ごとに重みの和で正規化し、修復例の総重みを単純に倍増させる方法とは区別する。
`--copy-margin-weight`は両指示の最初の異なるtokenだけで、正解logitがコピー側をmargin以上上回る損失を加える。
この位置までは両指示のtoken接頭辞が同じなので、同じ条件下の次tokenとして比較できる。
正常保持K・待機Wにはコピー負例を作らない。教師ラベルから作る学習専用注釈で、推論promptへ渡さない。
標準条件・差分CEのみ・差分CE＋コピー対照を同じデータ/親重み/学習回数で比較し、検証用の生成精度と正常保持で選択する。
不正指示が減った件数だけを精度改善とせず、有効だが誤った修復・保持への誤提案も数える。
学習後のGGUFは同じ局所出力契約であり、推論時に負例比較や別の教師モデルを要求しない。
