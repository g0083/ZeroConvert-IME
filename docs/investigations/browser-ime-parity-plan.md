# ZeroConvert IME Web 版 完全再現計画

> [!NOTE]
> **状態: 段階実装中**（Web Wasm プロトタイプは `web/` にて実装・検証進行中）。現行構成は [browser-ime.md](browser-ime.md)、最新の検証記録は [browser-ime-parity-2026-11-17.md](../../reports/web/browser-ime-parity-2026-11-17.md) を参照してください。

Web 版と配布済み Windows 版を比較したところ、4つの入力例の計43打鍵で、読みと先頭候補が一致した。この範囲ではモデルと通常変換の接続を確認できた。補正候補の到着順、確定境界、読みルビの表示、学習後の候補順まで揃えるには、Windows クライアントとサーバーが変換前後に担う処理を共有する必要がある。 [現行 Web 版の構成](browser-ime.md) · [公開ビルド](https://github.com/g0083/ZeroConvert-IME/actions/runs/43809266180)

## 完全再現の範囲

GitHub Pages の試用ページ内で、同じモデル・設定・学習データと同じ操作列を与えたとき、Windows 版と同じ読み、候補順、未確定文、確定文が得られる状態を目指す。候補一覧、インラインの読み・補正差分・先読み、選択状態、表示と消去の順序も照合する。比較基準は Windows の CPU 経路とし、最初の基準モデルには公開ページと同じ Nano v4.1 IQ4_emb8 を使う。GPU 版や別モデルを照合する場合は、同じ条件の Windows 側の記録を別途採取する。

ページは Web Worker 内で推論し、DOM 上の編集範囲とキャレットを操作する。Windows の TSF 登録、他アプリの編集範囲、OS のグローバルショートカットはネイティブ版が担う。再現したい挙動を「ページ内の操作」として記録し、TSF の通知や座標はブラウザ側の入力・フォーカス・表示位置に対応づける。 [Microsoft の TSF 仕様](https://learn.microsoft.com/en-us/windows/win32/tsf/text-services-framework) · [W3C Input Events Working Draft](https://www.w3.org/TR/input-events-2/)

| 領域 | 公開版の現在地 | 再現に必要な作業 |
| --- | --- | --- |
| 通常変換 | Windows と同じ Swift ソース・llama.cpp リビジョン・GGUF を使用 | Rust サーバーの候補加工とクライアントの状態遷移も照合し、通常候補の全件・順序・読み・消費範囲を検証する |
| ライブ変換・確定 | 自動確定に共有 Rust の判定を使用 | 自動確定後の変換継続、部分確定、文節移動、確定の取消と既存文の再変換を揃える |
| タイポ補正・先読み | 補正・先読みを要求する判定の単体ページがあり、Swift の通常変換はモデルに接続済み | Rust サーバーの補正・先読み生成、候補の合流、棄却・採用と取消をつなぐ |
| UI | 候補一覧の HTML・テーマ・スクロール処理を再利用 | 読みルビと補正差分、先読み表示、キャレット追従、キー・クリック・フォーカス時の開閉を揃える |
| 設定・学習 | 配布設定を元に CPU を指定し、学習を無効化 | 同じ設定を適用し、学習・候補の忘却・消去をブラウザ内で永続化する（設定の既定値と学習可否の共有判定、ブラウザ内保存まで実装。忘却 UI と実機照合は未実施） |

## 実装状況

CPU 版の Windows Swift DLL とローカルの Web Wasm に同じ操作を129回通した。読み、原打鍵、カーソル、候補全件と消費長は128操作で一致した。残る差は `okur` を打ったときの第3・第4候補の順序で、候補の集合と先頭候補は同じだった。先読みの5例では、Windows が提案した2例を Web は同じ時間制限内に返せなかった。辞書、設定、モデルの照合方法と Windows 実機で観察した範囲は検証記録に残した。 [検証記録](../../reports/web/browser-ime-parity-2026-11-17.md)

| 範囲 | ローカル実装 | 照合に残る作業 |
| --- | --- | --- |
| 入力・確定 | 共有ポリシーで候補移動、確定境界、削除を判定。Shift＋左右で Swift の文節境界を調整し、フォーカス移動後も確定文を保持する | 複数文節をまたぐ移動と再変換、学習を止めた Windows TSF の同条件トレース |
| 補正・先読み | 別の Worker で共有 Rust と llama.cpp を実行。通常候補を保持したまま、補正と先読みの表示、採用、補正の取消を処理する | 同一の CPU 設定で Windows 側のアシスト出力を採取し、誤補正・取りこぼし・先読みと遅延を比較する |
| 表示 | 候補 WebView と補正差分を再利用。読みルビとキャレットに追従する候補窓を Edge と Chrome で確認した | Windows と同じテーマ・倍率で位置と開閉順を比較する |
| 設定・学習 | 配布設定を基に Swift に設定を渡す。候補の採用、忘却、全消去を Swift で処理し、学習ファイルを IndexedDB に保存する | Windows と同じ採用履歴の比較。現在の Swift は読み取り専用モードで候補 ID を発行しないため、個別の忘却には学習モードの切り替えが必要 |

Web の初期設定では学習を `disabled` にする。設定欄で学習を有効にすると、ページ内で確定した候補を保存する。補正モデル側の採用履歴は、変換候補の学習とは別に接続する必要がある。


## 実装順と合格条件

### 1. Windows 版の操作記録を作る

比較に使う Windows ビルドのコミット、辞書のリビジョン、GGUF の SHA-256、推論設定、初期学習データを固定する。配布済み DLL との43打鍵は既存の回帰確認として残し、完全再現の判定には TSF クライアントから UI まで通る実機の記録を加える。通常候補と補正・先読み候補の合流後に、読み、未確定ローマ字、候補の種類・順序・消費長、カーソル、確定文、表示要素を操作ごとに採取する。候補 ID の発番が環境ごとに異なる場合は、採用・棄却・忘却が同じ候補に作用することを比較する。 [Windows の入力状態](../../windows/crates/client/src/engine/composition.rs) · [Windows の変換 RPC](../../windows/crates/server/src/main.rs) · [現行モデルの Web テスト](../../web/check-model-wasm.mjs)

操作列には `ashitanokaigi` と `nihongo` の通常入力、`okseri` と対応する正常入力、文脈つきの補正・先読み、未確定ローマ字の直後の Backspace を入れる。文中での左右移動と Delete、候補選択中の確定・取消、文節境界の変更、部分確定直後の続きも記録する。非同期の結果が前後する場面は、実機の記録に加え、結果の到着順を指定できるテストを使う。合格条件は、同じ条件で再実行できる操作列と期待結果が揃い、現行 Web 版との差分を各操作に結び付けられること。 [共有入力ポリシーの既存ケース](../../tests/input-policy/cases.tsv) · [自動確定の既存ケース](../../tests/input-policy/auto-commit-cases.tsv)

### 2. 変換セッションの状態遷移を共有する

Windows の Rust サーバーで行う候補加工と、Rust クライアントが担う入力モード、確定境界、変換継続のうち、OS 呼び出しを含まない処理を共有する。Web Worker は正規化したキーと編集イベントを共有処理に渡し、ページは結果から選択範囲と候補を描画する。Swift に渡す入力単位、Rust の文字数、DOM の UTF-16 オフセットを境界で変換し、削除とカーソル移動で差が出た箇所を個別に検証する。 [Web の変換セッション](../../web/pages/model-worker.mjs) · [Swift への Web 接続](../../web/ModelBridge.swift) · [Windows・Web で使う自動確定判定](../../windows/crates/shared/src/conversion_policy.rs)

合格条件は、通常変換の操作列について、全候補の順序・入力消費長・確定境界・未確定文が一致すること。候補表示中の編集、連打、フォーカス移動、ページ内の別の欄への切り替えでも、前の編集セッションの結果が新しい入力に混ざらないことを確認する。

### 3. 補正と先読みの非同期経路をつなぐ

Windows サーバーの補正・先読み生成と候補の合流処理を使い、Web 側から既存の `CompletionBackend` に接続する。Windows の推論要求を記録し、プロンプト、生成パラメーター、字句化、停止条件、結果の検証まで揃える。キーボード補正は `keyboard_repair` の入力と戻り値を照合し、通常変換で得た補正済みの読みと衝突しないようにする。モデル推論中も通常の打鍵を受け付け、補正と先読みの完了順が変わっても Windows と同じ条件で採用する。 [推論バックエンド境界](../../windows/crates/server/src/ai_assist/runtime.rs) · [共有エンジンのホスト API](../../engine/rust/src/bridge.rs) · [Windows の候補採用](../../windows/crates/client/src/engine/composition/typo.rs)

最初に応答を固定したテストで、通常候補の保護、補正優先、先読みの棄却、遅延結果の破棄を確認する。その後に実モデルへ切り替え、取りこぼし・正常入力への誤補正・先読みの妥当性・応答時間を比較する。合格条件は、採用と取消の結果まで一致し、古いリクエストやタイムアウトが確定済みテキストを書き換えないこと。ブラウザ載せ替えで推論結果が変わる場合は、プロンプトと推論器のどちらで差が生じたか特定し、該当ケースを回帰テストに残す。

### 4. 読み・候補・アシスト表示を揃える

既存の候補 WebView とテーマの再利用を続け、読みルビ、補正差分、先読みのマークアップと表示条件も Windows の実装から共有する。ブラウザでは編集範囲のキャレットに表示を追従させる。改行、選択範囲、拡大・スクロール、表示領域の端、フォーカス移動の挙動を確認し、候補のマウス選択で入力が途切れないようにする。 [Windows の候補 WebView](../../windows/crates/ui/src/candidate.rs) · [Windows の読み表示](../../windows/crates/ui/src/ruby.rs) · [Web 側の表示接続](../../web/pages/model-input.mjs)

合格条件は、同一の配色・文字サイズ・倍率で、候補順と選択行、ルビ、マーカー、開閉タイミング、確定前後の表示が対応すること。Edge と Chrome で目視と操作を確認し、対応ブラウザとして案内する環境は同じ操作列を通す。スクリーンショットでは候補窓の DOM・スタイルとキャレットからの相対位置を比較する。

### 5. 設定と学習を接続して公開判定を行う

配布時の設定を起点に、変換と表示に関わる設定、学習の有効・停止、候補の忘却、履歴の消去を接続する。ブラウザ側の保存先には IndexedDB を候補とし、エンジンには必要な学習データだけを受け渡す。サイト内で閉じるデータとして、設定・学習の形式と更新時の読み戻し方を決める。学習無効時、保存不能時、消去後、再読み込み後、複数タブから操作した場合の結果を確認する。 [Windows の学習削除計画](learning-deletion-plan.md) · [IndexedDB API](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)

合格条件は、学習が空の状態に加え、同じ採用履歴を再生した状態でも候補順と忘却の結果が一致すること。Windows の設定で個別に有効にする翻訳や外部再ランキングまで再現する場合は、モデル・通信先・資格情報の扱いを先に確定し、そのモードごとに Windows の比較記録を作る。

## 公開時の判定

- Windows の入力アプリと公開 URL の両方で同じ操作列を通す。Node の Wasm テストは既存の回帰確認に使い、ブラウザ実機で Worker、フォーカス、キャレット、候補操作、端末内保存を確認する。
- モデル・辞書・設定・初期学習データを揃えた試験で、読み、通常候補とアシスト候補、確定範囲、確定文、表示の状態遷移に未解決の差分がないことを確認する。追加モードと対応ブラウザは実際に確認した条件を記載する。
- 同じ測定機で初回起動、打鍵から通常候補の表示、補正・先読みの表示、ピークメモリを測る。許容する応答時間と対象端末は、最初の比較記録を取った段階で決める。単一スレッドのまま基準を満たせる間は、既存の GitHub Pages で配信する。
- Windows の共有層を変更した段階では対応するテストとビルドを行い、実 IME 確認には `Build-Trial.bat` で適用したビルドを使う。GitHub Pages は検証したコミットの Wasm・辞書・モデルを公開し、回帰時に戻せる直前の配信コミットを記録する。 [Windows の開発・反映手順](../development-workflow.md) · [Pages のビルド手順](../../.github/workflows/pages-smoke.yml)
