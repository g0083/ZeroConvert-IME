# ドキュメント作成・管理ルール

リポジトリ内のドキュメントが実コードと乖離したり、古い計画書・調査メモが現行仕様と混同されたりするのを防ぐための運用ルールです。

---

## 1. ディレクトリ別の役割と配置ルール

ドキュメントの新規作成・移動時は、性質に応じて次のディレクトリへ配置します。**ルートの `docs/` や `reports/` の直下に個別調査や一時レポートを直接置かないでください。**

| パス | 役割 | 置いてよい文書 |
| --- | --- | --- |
| `README.md` / `AGENTS.md` | プロジェクト全体の入口 | 概要、最新リリース、ビルド入口、全エージェント共通制約 |
| `docs/` | **現行仕様・恒久ガイド** | システム構成、ファイル地図、セットアップ、開発・配布手順、モデル資産仕様、現行変換ロジック、公開可能な学習/評価契約（§5参照） |
| `docs/investigations/` | **個別機能の調査・実装計画・障害解析** | 特定機能の設計/調査、バージョン別不具合解析、実装計画（後述のステータス明記が必須） |
| `reports/models/` | モデル性能比較レポート（公開用） | ZeroCon Model（Nano / Standard / Origin 等）の性能比較結果のスナップショット（§5参照） |
| `reports/port-history/` | Android 移植・復旧の履歴 | 移植各ステージの記録、完了監査、ソース復旧記録（歴史的記録） |
| `reports/web/` | Web / ブラウザ版レポート・HTML | ブラウザ版パリティ検証記録、外部向け紹介・比較 HTML |
| 各サブプロジェクト直下（`windows/`、`android/`、`engine/`、`data/`、`benchmarks/`、`web/`、`experiments/legacy/`） | サブプロジェクト固有の入口・規約 | 各ディレクトリの `README.md`、`AGENTS.md`、固有運用手順（`windows/docs/` 等） |
| `artifacts/results/`・`artifacts/logs/` | 実行ログ・機械生成結果（Git対象外） | ベンチマーク結果 JSON、ビルドログ、手動確認ログ |

### 一時ファイル・ログの禁止場所

- ルートやソースディレクトリ（`windows/`、`android/` 等）直下に `*.log`、一時差分テキスト、確認用メモを放置しない。不要になった一時ファイルは速やかに削除する。
- スクリプト断片は用途に応じて `scripts/`、`benchmarks/`、`experiments/legacy/` へ置き、`reports/` にコードを置かない。

## 2. ドキュメントのライフサイクルと古い文書の扱い

### 2.1 計画書・調査メモのステータス管理

`docs/investigations/` などに計画書（`*-plan.md`）や調査メモを作成する場合は、**冒頭（タイトル直下）に必ず現在の状態を明記**します。

```markdown
> [!NOTE]
> **状態**: 計画中 / 段階実装中 / 実装済み（YYYY-MM-DD） / 廃止・置換
> **現行仕様・実装先**: [関連する恒久仕様書やソースへのリンク]
```

- **実装完了後**:
  1. 恒久仕様書（`docs/architecture.md`、`docs/windows-conversion-logic.md`、`docs/android-conversion-logic.md`、`docs/android-shared-engine.md` 等）へ現行仕様を反映する。
  2. 計画書の冒頭ステータスを「実装済み（日付）」へ更新し、現行仕様書・実装ファイルへリンクする（または内容が恒久仕様書へ完全に統合され参照価値がなくなった計画書は削除する）。
- **方針変更・置換・廃止時**:
  - 廃止されたアーキテクチャ（例: 旧 18090 番独立 Corrector、CUDA バックエンド、`:app` Gradle モジュール等）に関する文書をそのまま現行手順のように残さない。
  - 歴史的記録として残す場合は、冒頭に `> [!WARNING]` または `> [!NOTE]` で「この文書は旧構成の記録であり、現在は [後継文書](...) が正本です」とリンクを書き足す。
  - 誰も参照していない一時的な個人メモ・重複ドラフト・陳腐化した作業ログは削除する。

### 2.2 恒久仕様書（`docs/`）の肥大化防止

- `docs/` の文書には**「いま動いているシステムの仕様・手順・制約」**を書く。
- 個別の作業日に実施した長いビルド検証ログや、特定コミット時点の試行錯誤の日記を恒久仕様書へ追記し続けない。検証記録は `reports/` または `docs/investigations/` に分離し、恒久仕様書からは必要最小限のリンクだけを残す。

## 3. 記述の正確性・単一情報源（Single Source of Truth）

1. **実体確認の徹底**: パス、ファイル名、関数・クラス名、ポート番号、設定キー、既定値、コマンド名は、必ず最新のソースコード・設定ファイルを確認して書く。記憶や古い別ドキュメントからの転記で書かない。
2. **正本の重複定義を避ける**:
   - Windows 版番号: `windows/app-version.json`
   - Android 版・SDK・NDK: `android/gradle.properties`
   - Windows モデルカタログ: `windows/deployment/model-catalog.json`
   - 共有入力ポリシー仕様: `tests/input-policy/cases.tsv` / `windows/crates/shared/src/conversion_policy.rs`
   - これら正本がある値は、必要な箇所だけ簡潔に示し、複数文書へ細かく複製して陳腐化させない。
3. **配布物に含まれる文書の注意**:
   - `windows/deployment/README.md` や `THIRD_PARTY_LICENSES.md` 等はインストーラー／配布パッケージにも同梱される。開発用の古い記述や未対応モデル名を残さない。
4. **リンク規約**:
   - ワークスペース固有の絶対パス（`file:///d:/...` 等）をドキュメントに書かず、相対パス（`../../...`）でリンクする。
   - ファイルを移動・削除・改名した場合は、リポジトリ全体で参照元を検索し、リンク切れを残さない。

## 4. インデックス整備と更新チェックリスト

新しい文書を追加・移動・削除したときは、同じ変更の中で次を確認します。

- [ ] 該当ディレクトリの `README.md`（[docs/README.md](README.md)、[docs/investigations/README.md](investigations/README.md)、[reports/README.md](../reports/README.md) 及び各サブディレクトリの `README.md`）に追記・反映したか
- [ ] 機能追加・廃止・設定変更に伴う既存の恒久仕様書（`architecture.md`、`file-map.md`、変換ロジック文書等）を更新したか
- [ ] 実装した計画書の「未実装」表記を「実装済み」または後継リンクへ更新したか
- [ ] 変更した `.md` 内の相対リンクが実在ファイルを指しているか
- [ ] 公開面に性能以外の内部詳細が含まれていないか（§5）
- [ ] `python scripts/check_repository.py` が通るか

---

## 5. 公開面の原則

公開面は**性能の結果のみ**を伝えます。詳細は（内部）に保存し、公開文書には具体的に書かず「（内部）」と示すにとどめます。リリース時の対外アピールはブログで行い、数値は本家のリリース文面・公開レポートと一致させます。
