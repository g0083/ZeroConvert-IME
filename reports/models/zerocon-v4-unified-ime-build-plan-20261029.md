# ZeroCon v4派生モデル構築計画 — 3機能の統合と入力方式別の開発

2026-10-29作成。Standard／Nano v4の変換能力を引き継ぎ、かな変換・タイポ補正・先読みを共通の重みで扱う。
ユーザー指定により、**Standard-QWERTY、Nano-QWERTY、Nano-Flickの3系統を必須**とする。

**状態：計画の正本。2026-10-29にStandard-QWERTYの研究用初版R5をHF・GGUF・Q8で作成した。補正の改善はあるが、通常変換の退行・保護pathの変形・正常誤変更が残り、品質条件は未達。結果は[Standard-QWERTY試作記録](zerocon-standard-qwerty-unified-20261029.md)を参照。Nanoの2系統と実IMEへの反映は未実施。本書の目標値は新モデルの達成実績ではない。**

## 1. 方針と成果物

R6の[改善検証](zerocon-standard-qwerty-unified-r6-20261029.md)では、compact入力と表記を直接返すrepairも研究比較する。
この表記出力を製品契約へ採用したとは扱わず、以下の品質目標やNano必須方針は維持する。

「3機能を1モデルへ統合すること」と「入力方式を1モデルへ統合すること」を分ける。
初期本線は入力方式別。各成果物が、かな変換・タイポ補正・先読みの3機能をタグで切り替える。

| 必須成果物・仮称 | 初期重み | 入力方式 | 主な用途 |
|---|---|---|---|
| ZeroCon Standard-QWERTY Unified | Standard v4 | 日本語ローマ字入力 | Windows等で変換精度を優先 |
| ZeroCon Nano-QWERTY Unified | Nano v4 | 日本語ローマ字入力 | Windows等でCPU応答・容量を優先、Androidの物理キーボード等も評価 |
| ZeroCon Nano-Flick Unified | Nano v4 | 日本語フリック入力 | Androidのソフトキーボード |

Nano-QWERTYはStandard版を作った後の任意の軽量化ではなく、独立した必須成果物とする。
Nano v4から直接追加学習する条件を必ず残し、改善したStandardからの蒸留は比較条件にする。
Standard-Flickは初期必須には含めず、Nanoの品質不足を調べる際の比較候補とする。

QWERTY/Flickをタグで切り替える共通モデルは後段の比較実験。統合による保守上の利点だけで採用しない。
同じ基盤・規模・元文・予算で入力方式別モデルと比較し、両方式の品質・遅延を満たした場合だけ置き換える。
Standard共通版とNano専用版の差を、入力方式統合だけの効果と報告しない。

各端末は選択されたモデル1本で3機能を処理する。3機能のために別々の重みを常駐させる構成を最終形としない。
モデル選択変更時の読み込みは許容するが、打鍵ごとの複数モデル読み替えは行わない。

## 4. タグと入出力契約

### 4.1 タスクと入力方式を別軸にする

| 軸 | 設定例 | 意味 |
|---|---|---|
| task | convert / repair / predict | 入力範囲の変換／誤入力の読み修復／後続suffix |
| input_method | romaji / flick / kana | 日本語ローマ字入力／フリック／かな直接入力 |
| layout | JP/US QWERTY、フリック配列ID | 取得・実装済みの配列。隣接誤りの規則を選ぶ |
| observed state | ctx, raw, reading, pending, surface, cursor, events, protected | 実際に観測できる状態だけを渡す |

QWERTYは物理配列、romajiは日本語の入力方式。英語のQWERTY入力を日本語ローマ字補正へ自動投入しない。
かな直接入力は正しい読みの変換を共通機能で扱えるが、その方式特有の誤打補正は別に学習・評価する。
未学習の方式・配列を既知のタグへ偽装しない。未対応の補正は無提案とし、通常変換を継続する。

外付けキーボードのあるAndroidでも「Androidだからflick」と決めず、現在の入力方式とモデルの対応表で選択する。
入力方式・モデルの切替時に旧世代の候補・KV・採用対象を無効化する。

### 4.2 出力の意味

#### ローマ字とひらがなの渡し分け

入力形式はtaskごとに固定する。通常変換に元ローマ字を直接渡して、日本語の読みへの復号から学び直す方式は初期本線にしない。

| 処理 | モデルに渡す主入力 | 表記の契約 |
|---|---|---|
| 通常convert・全方式共通 | IMEで復号した読み＋左文脈 | IME側の読みはひらがな基準。v4用codecで対応するかなだけをカタカナへ変換してモデルへ渡す |
| QWERTY repair | 元ローマ字raw＋pending＋左文脈 | ローマ字のまま渡す。誤りの手掛かりをかな化で失わない。正解かなは入力に含めない |
| Flick repair | 実際に入力されたひらがな＋取得済みイベント＋左文脈 | 元ローマ字は作らない。表示のカタカナ等を単純に破壊しないよう観測状態と読みを区別する |
| predict・全方式共通 | 現在の可視表記＋左文脈 | 漢字かな交じりをそのまま渡す。ローマ字やひらがなへ全体を戻さない |

repairの修復結果は両方式ともひらがな基準の読みへ統一し、convertのcodecへ渡す。
したがって、正常ローマ字入力はIMEの決定的な復号→convert、誤入力候補はraw→repair→修復読み→convert。
Flickは観測かな→repair→修復読み→convertで、同じ重みをtaskタグで再利用する。
英字・数字・URL・幅・空白・保護領域は、かなの表記合わせとは別に保持する。NFKCによる一括変換は行わない。
旧v4の比較器は`hira_to_kata`で読みをカタカナ化してPUA形式へ渡しているため、モデルへの「読みはひらがな」と一括記述しない。
初期のpredictはpendingが非空なら新規提案を控え、部分入力から先読みする拡張は別の学習・評価条件とする。

| task | 出力 | 守ること |
|---|---|---|
| convert | 指定された読み範囲の表記 | 未入力の語を付け足さない。数字・幅・空白・保護文字列を保持 |
| repair | 修復した読み、keep、abstain | 直接表記まで創作しない。keepは正常保持、abstainは判断不能 |
| predict | 現在の表記へ追加するsuffix、abstain | 可視prefixを再生成・変更しない。未確定入力の確定を勝手に行わない |

初期の補正経路は、読み修復→同じモデルのconvertとする。同じ重みを2回呼ぶので両段の時間を測る。
1モデル化を1回の推論化・常駐メモリ共有の保証とは扱わない。
cursorは選択範囲と読み／表記を区別して管理し、PythonのUnicode code pointとWindowsのUTF-16を境界で変換する。
イベントがない場合は「欠落」を明示し、gold側だけに読みやcursor欄を付ける等の正解漏れを作らない。

### 4.3 読みやすい表記の例

次のタグは設計例で、現時点のtokenizerに実装済みではない。実IDと各欄の有無・順序はP1で固定する。

```text
<task_convert><method_romaji><ctx>会議室の<reading>ヨヤク<out>予約<eot>
<task_repair><method_romaji><ctx><raw>argiatou<pending><out>ありがとう<eot>
<task_repair><method_romaji><ctx><raw>arigatou<pending><out><keep><eot>
<task_repair><method_romaji><ctx><raw>arigatok<pending>k<out><abstain><eot>
<task_repair><method_flick><ctx><reading>きよう<events>missing<out><abstain><eot>
<task_predict><method_flick><ctx>本日の議事録を<surface>共有<out>します。<eot>
```

「きよう」は「器用」等の正常入力にもなるため、観測情報なしに「きょう」へ補正しない。
例は契約説明用で、評価用正解データとして学習へ流用しない。

## 5. 既存語彙と変換能力の保全

既存6000語のID、BPE、BOS/EOS/PAD、PUA制御、ASCII空白の符号化を保つ。
新しいタスク／方式／状態タグは、既存予約IDとの衝突を検査してから末尾へ追加する案を第一候補とする。
語彙追加なしの既存token列による制御も短い対照実験にできるが、ユーザー文字列と制御を混同しない。
ユーザーがタグと同じ文字列やPUAを入力しても制御として解釈せず、通常データとして往復できるcodecを作る。

追加IDを使う場合はembeddingと出力headのサイズ・共有関係を確認し、既存行を変更せずコピーしたことを検査する。
新規行の初期化、optimizer対象、保存、adapter merge後の残存、GGUFへのtoken/mapping反映を明示する。
6000語のままの教師と語彙拡張した生徒に、そのまま全vocab KLを計算しない。

P1では同じ新モデルに、既存形式のconvertと新タグ形式のconvertを両方教える。
旧形式の回帰と新形式の回帰を別々に測り、製品の3タスクAPIを新形式へ統一するのは両方の品質確認後にする。
新prefixの生徒と旧prefixの教師は、正解targetの相対位置を対応付けて比較する。prompt全体の位置IDが同じとは仮定しない。

HF→F32/F16 GGUF→固定CPU実行器で、特殊ID、literalタグ、連続空白、全半角数字、結合文字、絵文字、EOSを検証する。
F32整合・F16の丸め・量子化後の品質を分け、不一致を「同じ」と報告しない。
GPT-2の学習済み位置埋め込みの上限を、RoPE設定の変更で延長できるとは考えない。

## 6. データ構築

元文書・元文・利用者・生成ID・派生元でtrain／validation／校正／確認／封印を先に分ける。
QWERTYとFlickで同じ元文を使う場合も分割を共有し、入力方式を変えて評価文を学習へ入れない。
既存480問と補正・先読みの評価ファイルは開発回帰として保持する。語彙追加・蒸留・量子化校正にも評価文を使わない。

| データ | 構築内容 |
|---|---|
| 通常変換 | 文脈有無、単語・文節・短文・長文、かな保持、固有名詞、数字・URL・コード |
| ローマ字補正 | 実ローマ字表の許容綴り、隣接・脱落・挿入・転置・連打、促音・撥音、未確定末尾 |
| フリック補正 | 採用配列の方向違い・隣接・濁点半濁点・小文字。取得済みイベントと文字だけの場合を分離 |
| 正常保持 | si/shi等の別綴り、意図的省略、固有名詞、正常な別語、削除途中、未確定子音 |
| 先読み | 句読点だけでなく内容語を含む短いsuffix、文中位置、文脈不足、完了文の無提案 |
| 編集状態 | 打鍵→削除→再入力、カーソル移動、範囲変更、確定／取消、方式切替 |

補正例はすべて同じ観測欄を持ち、正解読みをモデル入力へ入れない。
keep/emit/abstainの比率とctx有無の比率を別集計し、pending abstainを正常keep率に合算しない。
初期のrepair内配合はkeep65/emit25/abstain10を検査用の出発点とし、実際の誤打頻度の再現とは扱わない。
文脈を均す施策も一律採用せず、方式・状態別の誤変更と救済を比較する。
フリックの意図やタッチ方向を文字列から捏造しない。文字だけの誤入力から一意の意図を作れない例は無提案を許す。

承認済みMagpie由来データとUniDicの読み付与は候補だが、v4へ全量投入する前に短語句・文体・読みの品質を再点検する。
Originでは短語句の大量追加が改善につながらず、先読みemit正解の約3分の1が句読点等だった。
既存cacheは語彙が違うため再利用せず、元の承認済み行を新codecで再符号化する。
外部教師の生成は候補として保存し、人手／規則の検査を経る。教師の自己申告confidenceは採用確率に使わない。

最初は方式ごとに1万～5万の独立した承認元文を目安に小規模実験を行い、実在量を測って拡大する。
同じ文のノイズやprefix展開数、元文のunique量、処理tokens、target tokens、反復回数を別々に記録する。

## 7. 学習とv4の知見の継承

既存v4の主な実装は、CE・凍結教師KL・自己アンカーKL・対照マージン・EOS抑制・DoRA。
コード上の方式をそのまま「強化学習済みの効果」とは呼ばず、本計画ではまず教師あり追加学習と知識保全として継承する。
RL／選好学習は正確さ・正常保持・有用性を採点できるデータができてからの別実験とする。

初期task比はconvert60%、repair25%、predict15%。旧convert replayと新タグconvertの内訳をそれぞれ記録する。
方式別モデル内のtask配合と、repair内action配合を区別する。長いtargetが損失を独占しない正規化を基準にし、退行を検査する。

### 7.1 継承する施策と範囲

| 施策 | この計画での使い方 |
|---|---|
| 凍結した基盤の知識保全 | 独立した変更不能のv4コピーを使い、通常変換replayで既存能力を保持 |
| Dual Anchor／教師蒸留 | 通常変換で検証。未学習のrepair/predictに旧教師の出力を無条件に強制しない |
| Target-Corrected KL | 校正済み学習正解だけで検査。教師のlogit交換を正解の品質保証としない |
| Self-Copy Margin | 誤ったコピーだけを対象に比較。正しいひらがな・重複語・prefix保持を罰しない |
| EOS抑制 | taskごとの終了契約を守る。先読みの自然な「。」まで既存ID一覧で抑制しない |
| 層別LR／DoRA | 既存重みを大きく壊さない開始条件として使い、rank等は段階比較 |

語彙拡張時のアンカーは旧IDへ写像し、旧語彙内の分布保全と新制御tokenへの不要な確率流出を別に扱う。
adapterを無効にしても学習対象embedding等が変わっていれば元アンカーではないため、独立コピーとのhash・logit一致を検査する。
旧コードのEOS=3等やマージン2.2/3.0を、確認せず新しい全taskへ適用しない。

3系統の契約とデータ分割はP0/P1で同時に設計する。GPU学習は1ジョブずつ順次行う。
P3/P4はどちらかの不合格を理由に別の必須成果物を省略しない。

初期候補はDoRA rank16～32、LR2e-5～8e-5、BF16、context256～512とする。

### 7.3 GPU性能最大化プロファイリング（RTX 4070 12GB 最適化）
本学習（P3/P4）に入る直前に、小規模データによる100ステップのGPU飽和ベンチマークを実施し、ハードウェア性能を100%引き出すハイパーパラメータを固定する。
- **現状の課題意識**: 従来の小規模設定（microbatch=4等）ではVRAM消費が約4GBにとどまり、GPU消費電力も約130W（TDP 200W中）とTensor CoreやSM（ストリーミングマルチプロセッサ）が遊休している。
- **バッチサイズ飽和検証**:
  - `micro_batch_size` を 4 $\to$ **16, 32, 48, 64** へ順次引き上げ、VRAM消費を 8GB〜10GB 程度まで引き上げてTensor Coreの並列計算効率を最大化する（GPU消費電力を 180W〜200W のフル稼働域へ到達させる）。
  - 有効バッチサイズ（Effective Batch Size: 64〜128等）は `micro_batch_size × gradient_accumulation_steps` で数学的に一定に保ち、学習の収束性を維持しながら、カーネル呼び出しオーバーヘッドを最小化する。
- **データローダー & カーネル最適化**:
  - `pin_memory=True` および適切な `num_workers` を設定し、CPU側のデータ生成・転送待ちによるGPUアイドル（GPUストール）を根絶する。
  - PyTorch 2.x SDPA（Scaled Dot-Product Attention）を有効化し、アテンション計算のメモリ効率とスループットを極大化する。
- **本学習突入条件**: 1秒あたりの処理トークン数（tokens/sec）とGPU使用率（95%以上）、電力（170W以上）が最大となる最適設定をログに記録してからP3/P4の本学習ジョブを起動する。

新token行やheadを学習し保存する対象を明示し、adapterだけ保存して必要な行を失わないようにする。
改善が不足する場合だけrank拡大や部分／全パラメータ更新を比較し、最初から全設定を総当たりしない。
Stageごとに独立出力先を作り、コード・親・データ・乱数・optimizer・schedulerを保存する。

## 8. 評価・合格条件

「既存変換を維持して機能を追加できた」と「v4全体を超えた」は分ける。
初期の機能試作では変換退行をなくす。最終目標の引下げや、補正の一指標だけでの全面優越判定は行わない。

| 項目 | 判定方針 |
|---|---|
| 開発480問 | 最終目標Standard468以上、Nano466以上を継承。方式別3成果物を測る |
| 独立した変換 | 新規封印・校正済み正解で最良現行とのpaired差95% CI下限>0、+2ptを目標 |
| 保護文字 | 数字・全半角・空白・URL・コード等の重大な新規破壊0。カテゴリ別退行を確認 |
| 誤入力補正 | QWERTY／Flickそれぞれ実入力の読み救済90%を目標。最終表記と合成ノイズは別採点 |
| 正常入力 | 自動補正precision99.5%以上、正常誤変更率の片側95%上限0.1%未満を目標。救済率・採用率も併記 |
| 先読み | 同じ提示率で妥当性改善、同じ妥当性で打鍵削減20%改善を目標。prefix変更・創作・無提案を採点 |
| CPU遅延 | 通常変換と補正→変換の合計を別測定。Standardは現行Q8 p95比25%短縮、Nanoは現行Nano Q8以下を目標 |
| 端末負荷 | 全常駐モデル・KV・プロセス・容量を合算。Androidは実機のメモリ、電力、継続入力も測定 |
| 実IME | 打鍵・削除・移動・候補採用・確定／取消・方式切替の順序付きシナリオで確認 |

元の比較契約の条件は緩和しない。「全面優越」を主張する場合はStandardもNano Q8のCPU p95 59.86ms以下を目標とし、
容量・全常駐メモリも比較対象全体で確認する。封印評価の打切り・重複・暴走は0を要求する。
機能統合の試作合格を、これらの最終条件の達成に置き換えない。

件数の目安は実誤入力QWERTY/Flick各3,000、正常入力10,000、先読み2,000、編集操作200シナリオ。
同じ元文の派生を独立件数と見なさず、文書・利用者のクラスタを考慮する。
正常入力で独立2,995件すべて誤り0の場合でも片側95%上限がようやく約0.1%となる。
同じ文書の何千個のノイズでこの独立性を代用しない。
先読みは複数の許容解と人による有用性を評価し、句読点／機能語／内容語の内訳を併記する。

しきい値は校正区分で選び、設定を固定して確認区分へ適用する。正解読み・未来入力・期待文を採用判定へ渡さない。
候補がなければ確認区分から選び直さない。封印評価を見て調整した場合は新しい封印区分を用意する。
最終候補は複数seed・複数回測定で確認する。GPU学習と同時に測ったCPU時間を最終速度比較へ使わない。

## 9. 実行系と入力方式の扱い

モデルAPIはtask・input_method・layout・世代・選択範囲を明示する。
通常変換を優先し、補正と先読みは背景処理。古い世代・別cursor・別方式の結果は破棄する。
補正が通常候補を消したり、先読みがTabの採用対象を勝手に入れ替えたりしない。
英語・コード・パスワード等を扱う既存入力モードの動作を維持する。

QWERTY修復は元ローマ字とpendingを保存する。フリックは取得可能な実イベントだけを使い、文字だけの状態でも動作範囲を明示する。
モデルを切り替えても入力状態の正本はIME側に置く。キー入力、削除、確定等の状態管理をモデルへ移さない。
Windows／Androidが同じ常駐構成とは限らず、同じモデルを別processでロードすればメモリも増える。

初期統合は既存の辞書・変換経路・補正経路を比較と復旧のため保持し、合格した機能から試験反映する。
旧Origin計画にあるRust＋llama.cppへの移行は別の実装軸。Swift撤去や全面リファクタリングをモデル合格の前提にしない。
最終的な一本化を宣言する前に、旧専用モデルが実際にロード・呼出しされていないことと、置換後の全機能を確認する。

## 10. 保存先・実装予定

以下の新しいentry pointは予定であり、本計画書の作成時点で実装済みではない。

| 対象 | 予定先 |
|---|---|
| codec・契約 | `training/v4_unified_contract.py` |
| データ構築と独立監査 | `data/build_v4_unified_dataset.py`、`data/check_v4_unified_dataset.py` |
| 学習・resume | `training/train_v4_unified.py` |
| 3task・方式・paired比較 | `benchmarks/research/evaluate_v4_unified.py` |
| データとcache | `artifacts/datasets/v4-unified-<方式>-<版>/` |
| 学習run | `artifacts/checkpoints/zerocon-v4-unified-<規模>-<方式>-<条件>/` |
| 重み・配布物 | `artifacts/models/zerocon-v4-unified-<規模>-<方式>-<精度>/` |
| 結果・ログ | `artifacts/results/`、`artifacts/logs/` |

各runのmanifestに親重みの全hash、tokenizer/追加ID、データ台帳・分割、教師、入力方式、配列、学習設定、code、実行環境を保存する。
Python entry pointは既存規約どおり`python scripts/run.py <対象.py> [引数]`で実行する。
model cardには3taskの実績、対応方式、非対応状態、量子化後の精度、来歴、再現方法を記載する。
Windowsソース変更時は`windows/AGENTS.md`、Androidは`android/AGENTS.md`と開発手順を読む。
ソース編集・テスト・ビルド・端末反映・操作確認・梱包・Git保存を個別に報告する。

## 11. 着手順と現在の作業との関係

1. 必須3成果物のP0台帳を作り、float親と配布モデル、利用条件の確認状況を固定する。
2. 共有codecと方式別契約をP1で検証し、変換の互換性を先に確認する。
3. QWERTYのStandard／Nanoを同じ元文から学習し、Nano-Flickの実配列・データを並行準備する。
4. 3系統の追加学習・校正・量子化・独立評価を順次実行する。
5. 条件を満たした成果物だけ試験IMEへ統合する。共通方式モデルや追加蒸留は別の比較として進める。

作成時点ではOrigin T2の100M追加学習と、その終了後評価が稼働している。
この計画書の作成だけでそのジョブを停止・置換したり、新しいGPU学習を同時起動したりしない。
新本線へGPUを割り当てる際は、既存ジョブの終了または明示的な停止と保存状態を確認する。
現在のモデル・重み・未コミット変更・既存履歴は保全する。
