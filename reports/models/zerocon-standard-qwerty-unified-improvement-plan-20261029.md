# Standard-QWERTY統合モデルの改善案

2026-10-29。ユーザーからの改善案検討依頼に対し、現行corrector・既存ハイブリッド補正・統合R5を照合した。
**本書は実験開始前の改善案。後続の学習・評価結果は[R6検証記録](zerocon-standard-qwerty-unified-r6-20261029.md)へ保存した。**
R6dは補正ポリシー比較で改善したが通常変換に退行が残り、研究版として保留。実IMEへの適用は行っていない。
最終的に同じ重み1本で変換・補正・先読みを行う方針と、[構築計画](zerocon-v4-unified-ime-build-plan-20261029.md)の品質目標を維持する。

## 1. 推奨方針

まず最新の専用correctorを正しく比較対象に固定し、補正単独で成立する学習をStandard v4上に再現する。
その上で変換replay、先読みを順に加える。並行する方式比較では、補正文の自由生成に加えて、
打鍵・辞書から絞った候補を同じ統合モデルに選ばせる方法を試す。

現在のR5へ追加学習を繰り返すだけでは、基盤・入出力形式・学習量・タスク干渉のどれが原因か分からない。
診断用の補正専用重みを作ることは、製品に複数モデルを常駐させることを意味しない。

## 2. 確認した事実

### 2.1 比較対象は現行v3.2 XSmall

現行カタログと`ZeroConvertIME-windows/models/zerocon-model-corrector.gguf`は、
`artifacts/models/corrector-v32-xsmall-q4km.gguf`とSHA-256が一致する。
SHA-256：`dd87dbdc1a04cb4391f8429e6a1addc3c65d824996dd465e96803a5c1411fe2e`。
10月27日のv3.1系XSmallの26/255を現行の値として扱わない。

`artifacts/results/corrector-v32-xsmall-300.json`では、タイポ255件に正しい補正候補70、
誤提案46、正常45件への誤提案4。通常候補も含めた正解ありは74/255。
これはVulkan・通常モデルzenz-v3.2-small Q5を使う補正パイプライン評価であり、
統合R5のCPU・合成入力・読み一致評価とは直接比較できない。Swift・TSFも含まない。

現行学習の保存済みTrainingArgumentsとadapter、dataset-provenanceから確認した条件：

| 項目 | 現行専用corrector |
|---|---|
| 基盤 | zenz-v3.2-xsmallのローカルHF |
| データ | corrector-v2-20261027、train 40,111／val 3,081 |
| 学習 | 3 epoch、最終・選択step 3,762 |
| 学習率・実効batch | 2e-4、16×累積2＝32 |
| adapter | LoRA r16、alpha32、dropout0.05、c_attn/c_proj、DoRAなし |
| 出力 | 混在英字を含む観測読みと文脈から、漢字交じりの補正表記 |

max_lengthは前処理CLIの値であり、TrainingArgumentsからは確認できない。現行スクリプトの既定値を過去runの実値とは断定しない。
旧v3.1系の学習率1e-4・実効batch64の報告と、このv3.2 runを混同しない。

今回の統合データは同じcorrector-v2の正解読み・文脈を使っているが、元の学習例をそのまま全件replayしたわけではない。
かなの正解読みを確認できるものを選び、新たな合成rawとkeep/emit/abstainを作っている。
R5はさらに新規タグ、JSONで引用したフィールド、rawと観測読みの併記、ひらがな出力、3タスク化を同時に扱う。
これらの違いを「同じcorrectorの知見を移せた」と一括して扱わない。

### 2.2 R5では誤った生成も大きな問題

保存済みQ8生成を同梱codecの観測読みと突き合わせて再集計した。新しい推論は実行していない。

| 修復対象100件の出力 | 主コホート | corrector由来コホート |
|---|---:|---:|
| 正しい読み | 41 | 29 |
| 誤った別の読みへ変更 | 32 | 55 |
| 誤った観測読みをコピー | 19 | 6 |
| keepで補正なし | 7 | 10 |
| 形式違反 | 1 | 0 |

例えば`ogkai`（観測`おgかい`、正解`ごかい`）を`おおがい`へ、
`kqzoku`（観測`kqぞく`、正解`かぞく`）を`こくごぞく`へ変更した。
正解が一意でない例もあり、完全一致失敗の全件を人間にも明白な誤補正とは断定しない。
それでもコピー抑制だけでは、別の誤った読みに変える問題は解けない。

正常側にも`torihi`の観測`とりひ`を`とりひき`へ補完する例がある。
補正タスクへ先読みが混入したように見えるが、タスク干渉が原因かはまだ実験で分離していない。
削除途中・完結したprefixをkeepとする教師、文脈不足での保留、正常な別語を保持する例が必要。

R4の変更箇所CE＋誤コピーmarginは救済4/100・正常誤変更3/100へ悪化し、不採用だった。
追加のコピー罰や閾値緩和を、次の第一手にはしない。

再集計と保存済み学習条件の抽出：
`artifacts/results/inspect-unified-improvement-20261029.py`、
`artifacts/results/v4-unified-improvement-evidence-20261029.json`。

### 2.3 現行IMEの改善にはハイブリッド経路もある

[ハイブリッド研究](../typo-assist/keyboard-hybrid-20261027.md)の小型・厳しめ条件は、
予備集合690タイポの読み復元419件（60.7%）、正常345件の誤提案0件だった。
元打鍵から隣接キー候補を作り、辞書で最大8読みへ絞って読みLMで順位付けしている。
[Windows実IMEへの適用・確認](../typo-assist/keyboard-hybrid-ime-20261028.md)も記録されている。

これは専用corrector単体の70/255とは別の評価・経路であり、割合を直接比較しない。
ただし、統合モデルへ移すべき知見が「correctorの自由生成学習」だけではないことを示す。

## 3. 次の実験を行う順番

### E0：比較条件を固定する（学習なし）

- 親Standard v4、現行v3.2 corrector、R5、現行ハイブリッドのモデル・設定・実行器・辞書hashを固定する。
- 旧300問は観測読みからの補正を比較する開発評価に残す。元打鍵がない問題へ逆算rawを付け、実打鍵として統合モデルへ渡さない。
- 共通比較用に、raw・観測読み・文脈・pending・正解読み・許容表記が揃ったQWERTY集合を用意する。
  同じrawを固定decoderへ通した観測読みを専用correctorに渡し、統合版には契約どおりraw等を渡す。
  実IMEとの一致は入力テーブルだけでなく、削除・pending・カーソル状態でも別確認する。
- 最終表記は同じ通常変換バックエンドへ揃え、読み修復と表記生成を別採点する。
  表記を直接返す専用モデルは読み検証を通し、返却表記の成績も独立に残す。
- 生モデル、共通フィルター適用後、既存ルール等を含む全経路を分ける。全経路には別の同一条件測定が必要。
- 既存の300問、480問、ハイブリッド予備集合は既に開発へ使った集合として扱う。次の封印テストとは呼ばない。

ここで「現在使っている補正経路に対し、R5は何を失っているか」を特定する。

### E1：入出力を簡潔にし、文字列をそのまま扱う

現在のJSON引用は、入力pathのbackslashを重ねて出力する退行の原因候補。
普通の文字列はホスト側でcontrol ID認識を無効にしてそのまま符号化し、
欠損・空文字・フィールド境界は専用control IDで区別するcodec候補を作る。
必要なtaskのフィールドだけを使い、不要な`null`列を省く。rawと観測読みは別の情報として保持する。

旧IDは維持し、新しいcontrolは末尾追加する。文字列中の見かけ上のタグも、ホスト符号化でデータIDとして扱う。
path・URL・空白・引用符・絵文字・タグ文字列の往復、整数IDによるHF/GGUFの一致を先に確認する。
R5の重みに新codecだけを差し替えて改善済みとはしない。新旧形式を比べるなら同じ親・学習データ・予算から対照を作る。

### E2：Standard v4で補正能力の基準を作る

R5の継続だけでなく、元のStandard v4から診断用の補正専用モデルを作る。
現行correctorの再現に近い条件を起点にし、まず新規タスク学習そのものが成立するかを確認する。
学習率2e-4等をStandardで安全・最適と決めず、短い学習の実生成と正常保持で診断する。

| 比較 | 固定するもの | 変更するもの |
|---|---|---|
| 表記出力 vs 読み出力 | Standard v4親、同じ観測入力・文脈、同じ例・分割・予算・adapter | 教師を補正表記／正解読みへ切替 |
| 観測読み vs 観測読み＋raw | 選んだ出力形式、元文・例・予算 | 入力にraw情報を加える効果 |
| 補正専用 vs 統合 | 同じ入出力、repair教師・正例露出量、基盤 | convert/predict学習を加える効果 |

最初の表記／読み比較は、両方の教師を検証できる共通部分だけで行う。
読みを検証できない例を片方だけ除いて、その差を出力形式の効果とはしない。
fullデータ再現を追加する場合は別条件とする。過去の読み出力化の失敗も再検証対象に含める。

現行のデータ分離検査を再実行し、現在の全評価集合へ接する元グループを除外する。
旧rawが保存されていない例は観測入力用に使い、raw併用比較は実rawまたは来歴付きの新合成rawがある部分で行う。
step数だけでなく、修復正例の実サンプル回数・ユニーク例の被覆・target token数・計算量を記録する。

表記出力を製品案に採る場合は現計画のrepair出力契約を変更する必要がある。
読み出力を先に正解と決めず、精度・読み一致・総遅延を比較してから判断する。

### E3：キーボード・辞書候補から選ぶrepairを比較する

自由生成で誤った別の読みへ移る例が多いため、有力な比較案。
入力そのまま・既知の局所編集・辞書から、上限付きの候補集合を作る。
同じ統合重みのrepairタスクが候補を選ぶ方式を、同じ条件の自由生成と比較する。
これはキーボード用LMを別に常駐させる案ではない。

- 正解の候補被覆率を先に測る。候補がない問題は選択学習で救えない。
- 最初は実績のある隣接1打鍵から始める。脱落・転置等の拡張は種類ごとに被覆率と候補上限を測り、無制限探索にしない。
- 無変更と保留を選べるようにする。候補一覧があるだけで補正必須にはしない。
- 候補順の入替でも結論が安定するか検査し、位置だけを学ぶことを避ける。
- 候補選択の内部表現から外部の修復読みに戻す。新しい入力／内部出力契約が必要であり、R5へ推論時制約を付けるだけで成立とはしない。
- 専用correctorやハイブリッドの成功例は、正解読み・表記と一致したものだけを教師候補にする。
  検証・評価例や、その派生を学習へ戻さない。モデル同士の一致だけを正解保証にしない。
- 最大8候補は既存実験の起点であり、Standard統合版の精度・CPU遅延を保証しない。

候補方式が不利なら自由生成を残す。両者を併用する場合も、同じ重み・同じ要求予算での実測を条件とする。

### E4：成立した補正を変換・先読みへ統合する

E2/E3の有望な条件へ、まずconvert replayを加え、次にpredictを加える。
通常変換の教師は独立して凍結した元Standard v4とし、repair/predictへ未学習の旧教師を強制しない。
学習配分は段階的に戻し、各段階で補正の退行を測る。R5のrepair85%を最終運用分布として固定しない。

変換維持のKLとrepairの勾配が干渉する可能性は仮説である。E2の同形式比較で差が出てから、
task別の勾配量や層を調べ、adapter対象・層別LRを比較する。rank増加・全層学習・モデル大型化を先に一括実行しない。
統合段階での旧adapter固定・新adapter等は、最終的に静的merge可能かを確認する。打鍵ごとの重み切替を前提にしない。

### E5：checkpoint選択と採用判定を実生成へ合わせる

R5は11群のmacro CEで600stepを選択した。容易なabstain群等も含む平均lossは、修復成功率そのものではない。
別の固定validation元文で実生成し、正常保持・形式・保護文字を制約に、補正の正答／誤提案と通常変換の退行を比較する。
480問の既知評価をcheckpoint選択へ直接使う方法には変更しない。

- 正常な別綴り・固有名詞・英数記号・短語・削除prefix・pending・文脈不足を含むhard negativeを用意する。
- 完全一致だけでなく許容解を監査し、誤り種別・文脈量・入力長で分ける。
- モデル選択、提案閾値、自動適用閾値はvalidationで決め、封印前に固定する。提案率と自動適用率を混同しない。
- 正常100件で誤変更0でも、誤補正率0.1%以下を証明できない。独立な正常約3,000件で0件なら、
  二項モデルの片側95%上限が約0.1%になる。派生例同士の依存や実使用との分布差も残る。
- 親Q8とのpaired変換比較、保護文字の完全保持、先読み妥当性、CPU・実IMEの総遅延を別測定する。
  過去のVulkan 11msと統合CPUのHTTP時間は比較しない。

## 4. 最初の実行単位と進退判断

第一段階はE0の共通評価器・ケース整備と、E1のcodec試作。長時間の学習前に入出力と採点を固定する。
次にE2の表記／読みの対照2本を作る。そこで専用基準が弱ければ、統合へ進まず入力・教師・学習量を調べる。
基準が成立したらE3の候補選択比較、E4の統合へ進む。全条件を一度に掛け合わせる巨大な探索は行わない。

| 観測 | 次の判断 |
|---|---|
| 補正専用でも弱い | 入出力・教師・合成誤り・学習露出を優先。3タスク干渉とは断定しない |
| 専用は良く、統合で落ちる | replay配分・KL・adapter共有による干渉を調べる |
| 候補被覆は高いが選択を誤る | 順位学習・文脈・無変更との校正を調べる |
| 候補被覆が低い | 候補生成を改善。順位モデルの学習量だけを増やさない |
| 読みは正しいが表記が誤る | 共通変換バックエンド・文脈受け渡しを調べる |
| 点数は良いが正常誤補正／遅延が悪い | 採用せず保持・保留・処理予算を見直す |
